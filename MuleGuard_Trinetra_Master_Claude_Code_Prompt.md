# 2. Core product philosophy

The system must embody:

> **Sees the mule. Spares the look-alike. Never certifies the unseen.**

Meaning:

1. **Sees the mule**
   - Detect accounts whose current behaviour resembles known mule behaviour.

2. **Spares the look-alike**
   - Protect legitimate high-throughput accounts, businesses, hacked customers, coerced victims, and uncertain cases from automatic punitive action.

3. **Never certifies the unseen**
   - Never label an account “permanently safe.”
   - The low-risk state is “not currently flagged; continue monitoring.”

The ML model predicts behavioural risk, not criminal intent. A suspicious score is not proof that an account holder knowingly participated in fraud.

Final action must remain human-governed.

# 10. Split strategy and validation hygiene

Because positives are extremely rare, implement two complementary evaluation tracks.

## 10.1 Primary competition evaluation

1. Create one immutable stratified locked test split with fixed seed.
2. Ensure it contains a defensible minimum count of positive examples.
3. Save exact row indices to `data/splits/locked_test_indices.parquet`.
4. Never touch this split during feature selection, tuning, calibration, stacking, or threshold design.
5. On the remaining development set run:
   - repeated stratified 5-fold cross-validation
   - default 5 repetitions where compute allows
   - fewer repetitions in CPU mode, but never fewer than 2 without documenting why
6. Save every fold assignment.

All steps must be inside each fold:

- imputation/type conversion learned from training fold
- encoding
- filtering that depends on training statistics
- feature selection
- model fitting
- hard-negative mining
- calibration
- threshold selection
- ensemble fitting

## 10.2 Out-of-time stress test

If `F2230` truly represents chronological snapshot month and the values support ordering:

- train on earlier months
- test on the latest month
- do not shuffle across time
- report this as an out-of-time stress test, not the primary leaderboard metric
- verify that using `F2230` itself does not leak future information

If temporal interpretation is uncertain, do not pretend it is a valid time split.

## 10.3 Group leakage

Search for duplicate accounts, repeated entities, or correlated row identifiers. If discovered, use grouped splitting.

# 18. Lens 2 — False-positive protection

Implement a hard-negative verifier.

## 18.1 Hard-negative mining

Using OOF predictions only:

- identify legitimate accounts with highest false-positive scores
- define hard-negative bands
- compare their interpretable attributes and missingness patterns
- train a verifier on:
  - confirmed positives
  - hard negatives
  - a sampled background of regular negatives

Never mine hard negatives from the locked test set.

## 18.2 Probability calibration

Compare:

- Platt/sigmoid scaling
- isotonic regression
- optional beta calibration if implemented robustly

Select by:

- Brier score
- ECE
- calibration curve stability
- positive count sufficiency

With very few positives, prefer simpler calibration when isotonic overfits.

## 18.3 Conformal abstention

Implement split- or cross-conformal prediction, using MAPIE only if the installed API is compatible and tested. Otherwise implement a documented conformal procedure directly.

Possible outputs:

- `HIGH_RISK_SET`
- `LOW_RISK_SET`
- `UNCERTAIN_SET`
- `OOD_REVIEW`

The system must be allowed to abstain.

# 19. Lens 3 — Missed-mule and novelty challengers

These components are second opinions. They must not silently override the supervised model.

## 19.1 Isolation Forest

- fit on development/training data only
- preferably model the legitimate cohort
- tune contamination without using locked-test labels
- convert anomaly score to percentile
- use as disagreement signal

## 19.2 Positive-unlabelled learning

Run only after label-trust audit.

Conditions:

- labels `0` may contain undiscovered mules
- positive labels are reasonably reliable
- performance is evaluated carefully

If assumptions cannot be supported, keep PU learning disabled and document why.

## 19.3 OOD detection

Detect inputs unlike training data using a combination of:

- missingness-profile distance
- selected-feature range violations
- robust covariance or Mahalanobis distance on reduced features
- nearest-neighbour distance
- model disagreement
- prediction entropy
- category/schema novelty
- optional PCA reconstruction error

OOD must route to review rather than receive a confident normal decision.

## 19.4 Never certify clean

Use:

- `MONITOR`
- `NOT_CURRENTLY_FLAGGED`

Never use:

- `PERMANENTLY_SAFE`
- `CERTIFIED_CLEAN`

# 22. Ollama local analyst assistant

## 22.1 Correct role

Ollama is an optional explanation/reporting layer only.

Default local model:

- `qwen3.5:4b` for 16 GB RAM environments

Optional:

- `qwen3.5:9b` for stronger hardware

Make model name configurable.

Ollama must never:

- calculate risk
- change risk
- invent a transaction amount
- invent a feature
- infer criminal intent
- select a threshold
- freeze or block an account
- override the policy engine
- create evidence not present in the structured input

## 22.2 Structured input

Pass only verified structured data such as:

```json
{
  "account_reference": "ACC-1029",
  "calibrated_risk": 0.92,
  "risk_tier": "CRITICAL_REVIEW",
  "model_agreement": 0.88,
  "conformal_status": "HIGH_RISK_SET",
  "ood_status": "IN_DISTRIBUTION",
  "top_reasons": [
    {
      "feature": "F1702",
      "value": 10.4,
      "legitimate_percentile": 99.2,
      "direction": "INCREASES_RISK",
      "shap_contribution": 0.21,
      "verified_semantic_name": null
    }
  ],
  "allowed_checks": [
    "VERIFY_KYC",
    "CHECK_DEVICE_HISTORY",
    "CHECK_REGISTRY",
    "ANALYST_REVIEW"
  ],
  "limitations": [
    "Behavioural risk is not proof of intent",
    "Final action requires human review"
  ]
}
```

## 22.3 Structured output

Enforce JSON schema:

```json
{
  "summary": "string",
  "risk_tier": "CRITICAL_REVIEW",
  "verified_risk_score": 0.92,
  "reason_codes": ["string"],
  "recommended_checks": ["string"],
  "limitations": ["string"]
}
```

Use:

- temperature 0
- structured outputs / JSON schema
- Pydantic validation
- maximum response length
- timeout
- retry once
- circuit breaker
- no external network requirement

## 22.4 Hallucination validator

Reject LLM output if:

- risk score differs
- risk tier differs
- a feature not supplied is mentioned
- an unsupported amount/date/person is invented
- criminal guilt is asserted
- an action outside the allowlist appears
- required limitations are missing
- JSON is invalid
- response times out

Fallback to deterministic templates.

Create unit tests that intentionally force malformed and hallucinatory outputs.

The scoring endpoint must remain fully operational if Ollama is down.

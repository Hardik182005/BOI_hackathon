# Final Performance Report

Live evidence: `artifacts/testing/performance_results.json` (regenerated by
the QA harness on this machine — i5-1135G7, 16 GB, CPU-only).

## Measured figures

| Metric | Value |
|---|---|
| Cold backend startup → ready | ~8–12 s (bundle load included; health-gated by run.sh) |
| Single-row API latency | p50 and p95 recorded in the JSON (sub-second p50 after warmup; first call includes SHAP warm paths) |
| Batch throughput | **688 rows/s** on the 1,818-row locked-test batch (in-process); HTTP path chunked at 500 rows with progress audit events |
| Concurrency | 5 and 10 parallel scoring requests: all 200 OK, no state corruption (deterministic outputs) |
| Model bundle size | recorded in JSON (~tens of MB, joblib-compressed) |
| Peak RAM | scoring keeps >2 GB headroom on 16 GB (checked live); training peak governed by Mode A settings (n_jobs=4) |
| Frontend first render | Vite dev-server responds immediately; production build passes (~600 KB gzipped bundle) |

## Engineering guarantees

- Model loaded **once** at startup — no per-request reloads (verified by
  latency stability across repeated calls).
- No unbounded memory growth: batch scoring is chunked; SHAP explanations are
  optional per request; DB writes are transactional.
- Timeouts: narrator 120 s with circuit breaker; DB busy timeout 15 s; API
  client timeouts documented.
- Rate limiting: 240 req/min per client — demo-scale guardrail.
- One-command runner defaults are sized for 16 GB (single uvicorn worker;
  LightGBM/CatBoost/XGBoost inference is single-digit-ms per row).

## Scale honesty

These are single-node CPU demo numbers. Production sizing (multiple workers,
PostgreSQL, GPU challengers) is a documented extension, not a claim.

# Historical Metric Reconciliation

Final-validation prompt §7. Every headline number this repository has ever
produced is traced here, explained, or declared unreproducible.

The rule §7 sets is not "show the numbers" — it is:

> If a historical result cannot be reproduced, say so. **Do not silently select
> the most flattering historical number.**

That rule has teeth here, because the most flattering number in this repository
is **0.82423** and it is wrong twice over: it belongs to a **retired** model,
and that model was trained on a feature set that contained **quarantined**
features. It also sits at two of the filenames the spec itself names. This
document exists so that number can never be quoted by accident.

Generated by `scripts/reconcile_history.py` →
`artifacts/metrics/historical_reconciliation.csv`. The table below is that
script's output, not a transcription.

## 1. The control that makes any of this comparable

Two generations of results exist. They differ in **two** ways at once — the
feature sets were rebuilt behind the Feature Availability Firewall, and the
repeat count dropped from 5 to 3. A raw generation-1-vs-generation-2 delta
confounds the two, so before comparing anything, the split itself had to be
proved constant.

| Check | Result |
|---|---|
| Development rows, `n_repeats=5` | 7,264 rows, SHA-256 `d22b64295c06e506` |
| Development rows, `n_repeats=3` | 7,264 rows, SHA-256 `d22b64295c06e506` |
| **Identical development rows** | **Yes** |
| Fold assignment, repeats 0–2 | **byte-identical** between the two configurations |
| `dummy_prevalence` PR-AUC, gen 1 | 0.00870817708522955 |
| `dummy_prevalence` PR-AUC, gen 2 | 0.00870817708522955 |
| **Control delta** | **0.00000** |

The dummy classifier is the control. It has no features and no
hyperparameters, so if the split or the evaluation code had changed, it would
have moved. It did not move at all. Generation 2's three repeats are a strict
prefix of generation 1's five.

This is what licenses the rest of the document: **every remaining difference is
attributable to the feature sets, and nothing else.**

## 2. Root cause — generation 1 was trained on quarantined features

The firewall was built *after* generation 1 ran. Checking generation 1's stored
feature sets against today's 13-feature quarantine list:

| Compact set | Generation 1 (2026-07-10) | Generation 2 (2026-08-12) |
|---|---|---|
| `top_15` | **F3898, F3913, F3914** | NONE |
| `top_30` | **F3898, F3913, F3914** | NONE |
| `top_60` | **F3898, F3913, F3914, F3916** | NONE |
| `top_120` | *(did not exist)* | NONE |
| `top_250` | *(did not exist)* | NONE |
| `freq_ge_0.6` / `freq_ge_0_70` | **F3898, F3913, F3914** | NONE |
| `freq_ge_0.8` / `freq_ge_0_50` | **F3898, F3913, F3914** | NONE |

Every generation-1 compact set carried at least three quarantined features.
`top_60` — the set that produced the champion of that era — carried four,
including `F3916`, which is one of the three fields held at
`QUARANTINE_UNTIL_PROVEN_PRE_DECISION` because it could not be shown to be
available before the mule decision was taken.

**Consequence: no generation-1 number is admissible as a performance claim.**
They are recorded here as history, not as evidence.

### How to read this honestly

The measured seed-noise floor for this dataset is **0.0905 PR-AUC**
(`artifacts/metrics/seed_variance_v2.json`), and this project's published rule
is that *differences smaller than that spread are not real differences*.
Applying our own rule rather than a convenient one:

- **Three rows moved by more than the noise floor** and are real:
  `lightgbm_top_15` (−0.27678), `lightgbm_full_pool` (−0.16696),
  `catboost_top_60` (−0.12887).
- **Five rows did not.** `lightgbm_top_30`, `lightgbm_top_60`, `tabpfn_top_60`,
  `xgboost_top_60` and the dummy all moved less than 0.0905. For those, the
  correct statement is *"removing the quarantined features did not measurably
  change this model"* — not *"it got slightly worse"* or *"slightly better."*
- **The repeat-count effect is immaterial everywhere.** The largest
  `Δ repeat count` is 0.032, a third of the noise floor. Dropping from 5 repeats
  to 3 did not change any conclusion.

### What the pattern means

The damage was not uniform, and the shape of it is informative:

- **The smaller the feature set, the more the leak mattered.** `top_15` lost
  0.277; `top_60` lost 0.084. With only fifteen slots, three leaky features are
  a fifth of the model.
- **CatBoost leaned on them hardest** (−0.12887) and was the generation-1
  champion largely because of it. Its crown did not survive the firewall.
- **XGBoost and TabPFN did not depend on them at all** (+0.017, +0.014, both
  inside noise). The current champion family is the one that was never leaning
  on the quarantined fields — which is a reason for mild confidence in it, not a
  coincidence to celebrate.

### Not comparable, and why

| Generation-1 entry | Why it has no generation-2 counterpart |
|---|---|
| `logistic_l2` (0.23283) | generation 2 replaced full-pool L2 with `logistic_top30` (0.08816). The feature pool **and** the penalty both changed. Quoting a delta here would be meaningless. |
| `lightgbm_baseline` (0.61416) | never a candidate. It survives only as the **ACCEPTED** arm of the F3912 leakage ablation. |
| `REJECTED_leakage_lgbm_with_F3912` (0.94190) | a deliberate leak demonstration. It exists to be rejected. It is the highest PR-AUC in the repository and it is **not a result**. |

## 4. The champion has two OOF numbers. Both are real; only one is the model's.

`xgboost_top_120` is quoted in this repository as both **0.76904** and
**0.80465**. They are not a discrepancy and neither is wrong — they answer
different questions, and conflating them would overstate the system by four
points.

Measured directly from `artifacts/predictions/oof_v2.parquet`:

| Quantity | Value |
|---|---:|
| Per-repeat PR-AUC | 0.74927 / 0.80668 / 0.75117 |
| **Mean of the per-repeat PR-AUCs** | **0.76904** ± 0.02663 |
| PR-AUC of the repeat-**averaged** raw score | 0.80811 |
| PR-AUC of the repeat-averaged **rank** | 0.79329 |
| PR-AUC reported in `lens_stack_oof_v2.json` (averaged + calibrated) | 0.80465 |

So the +0.039 gap is **the averaging order, not the calibration**. Averaging
three repeat score-vectors is a three-seed ensemble, and it buys +0.03907.
Platt calibration then *costs* −0.00346 — it is applied for probability quality,
not for discrimination, and it is not free.

**Which number describes the product?** `0.76904`, the selection metric. The
served bundle is refit **once** on all development rows at a single
`GLOBAL_SEED` (`src/muleguard/cli/build_lenses_v2.py`); it does not average
three seeds at inference. `0.80465` describes a three-seed average that the
product does not ship.

Note also that +0.039 is itself **below the 0.0905 noise floor**, so we do not
claim seed-averaging is an improvement either. It is a variance-reduction
artefact of how OOF scores were pooled.

> **Adopted:** `0.76904 ± 0.02663` is the development OOF figure quoted for the
> champion. `0.80465` may appear only where it is labelled as the
> repeat-averaged calibrated basis on which the calibrator was fitted.

### A real defect this reconciliation exposed

The calibrator, the conformal sets and the frozen operating thresholds were all
fitted on the **repeat-averaged** score distribution (`_repeat_avg`,
`build_lenses_v2.py`), while the **served** scorer is a single fit. Those are
different distributions, and the difference is not cosmetic:

| Raw score cut | Accounts flagged, repeat-averaged | Accounts flagged, per single seed | Spread |
|---:|---:|---|---:|
| > 0.50 | 54 | 54 / 56 / 74 | 20 |
| > 0.20 | 113 | 99 / 102 / 162 | 63 |
| > 0.10 | 193 | 143 / 143 / 285 | 142 |
| > 0.05 | 315 | 219 / 219 / 477 | 258 |

At a raw cut of 0.10 the single-seed alert volume ranges from 143 to 285 — very
nearly a factor of two — while the averaged basis the thresholds were fitted on
sits at 193. **The frozen thresholds therefore carry an alert-volume
uncertainty that their point values do not show.**

This is recorded as an open risk, not silently fixed: correcting it means
either serving an average of several seed-fits (matching the calibration basis)
or refitting the calibrator on single-repeat OOF, and both change a frozen,
sealed bundle. It is carried into the release risk list rather than patched
late. Discrimination ranking is unaffected — Platt is monotone — so this is a
**probability-and-volume** issue, not an ordering issue.

| Value | Model | Where it is written | Status |

| 0.86077 | `lightgbm` agreement model | `locked_test_metrics.json` → `agreement_model_lightgbm_pr_auc` | retired; a secondary agreement model, never the scorer |
| **0.72627** | `xgboost_top_120` | `organiser_dry_run.json` → `offline_label_comparison` | the current champion's only locked-test result |

Both files that carry **0.82423** describe themselves as *"LOCKED TEST (single
touch, natural prevalence) — production scorer catboost_tuned_top60."* That
model is no longer the production scorer, and its `top_60` feature set contained
four quarantined features. Its ROC-AUC of 0.99399 and Brier of 0.00258 are
contaminated for the same reason.

The gap between the retired 0.82423 and the current 0.72627 is **not** a
regression. It is what the firewall cost — the same effect the table in §3
measures on development data, showing up again on the held-out split. Presenting
0.82423 as the system's accuracy would be presenting a leak as a result.

`artifacts/metrics/holdout_metrics.json` has already been rebuilt to carry
`current_champion`, `dev_oof_reference` and `retired_run` as explicitly separated
blocks. The two `*locked_test_metrics.json` files are left in place, unaltered,
as historical record — they are evidence of what was measured on 2026-07-10, and
deleting them would be tidying away the audit trail. They are listed here so
that no reader mistakes their filename for authority.

## 7. Rules adopted from this reconciliation

1. **A metric is quoted with its model, its split, its protocol and its data
   version, or it is not quoted.** Most of the confusion above came from
   filenames outliving the models they described.
2. **The selection metric and the reporting metric are the same number.**
   `0.76904 ± 0.02663` for the champion.
3. **The seed-noise floor is applied against our own claims first.** Five of the
   eight rows in §3 moved less than 0.0905 and are reported as "no measurable
   change," even where a larger claim would have flattered the firewall.
4. **A superseded artifact is annotated, never quietly deleted**, and never left
   as the only occupant of a spec-named filename.
5. **The highest number in the repository (0.94190) is a rejected leak.** That
   is the permanent reminder of why none of this is optimised for the biggest
   figure.
